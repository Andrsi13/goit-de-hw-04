# goit-de-hw-04 — Apache Spark. Оптимізація та SparkUI

Три варіанти однієї програми PySpark (Spark 3.5.5, `local[*]`, `spark.sql.shuffle.partitions = 2`) і аналіз вкладки **Jobs** у SparkUI.

Датасет: `nuek-vuh3.csv` (San Francisco Fire Department Calls for Service). Через розмір його немає в репозиторії; покладіть файл поруч зі скриптами.

| Файл | Що змінено |
|---|---|
| `hw_04_part1.py` | базовий варіант, один `collect()` |
| `hw_04_part2.py` | додано проміжний `collect()` |
| `hw_04_part3.py` | проміжний `collect()` + `cache()` |

## Частина 1 — 5 Jobs

![Частина 1](screenshots/part1_jobs.png)

- **Job 0** — `csv`: зчитування першого рядка для `header=true` (назви колонок).
- **Job 1** — `csv`: прохід по всьому файлу для `inferSchema=true` (визначення типів колонок).
- **Jobs 2–4** — один `collect()`. У плані два shuffle (`repartition(2)` і `groupBy`), тому він ділиться на 3 стадії, а AQE запускає кожну стадію з shuffle окремим job:
  - Job 2 — читання CSV + shuffle `repartition(2)`;
  - Job 3 — `where` + `select` + часткове агрегування + shuffle `groupBy` (2 задачі = 2 розділи; попередня стадія — skipped);
  - Job 4 — фінальний `count`, `where("count>2")`, повернення результату драйверу (1 задача — AQE злив 2 малі розділи в 1).

Трансформації (`where`, `select`, `groupBy`, `count`) ліниві й не створюють jobs; `where("count>2")` виконується всередині останньої стадії.

## Частина 2 — 8 Jobs

![Частина 2](screenshots/part2_jobs.png)

- **Jobs 0–1** — читання CSV (header + inferSchema).
- **Jobs 2–4** — проміжний `collect()`: повний ланцюжок з двома shuffle.
- **Jobs 5–7** — другий `collect()`: **той самий ланцюжок виконується знову з нуля** (Job 5 — `1/1` без skipped, тобто CSV перечитано, shuffle перезаписано) + `where("count>2")`.

Проміжний результат ніде не збережений, тож кожна дія будує обчислення від джерела. Звідси +3 jobs порівняно з частиною 1.

## Частина 3 — 7 Jobs

![Частина 3](screenshots/part3_jobs.png)

- **Jobs 0–1** — читання CSV (header + inferSchema).
- **Jobs 2–5** — перший `collect()` над DataFrame з `cache()`: shuffle `repartition` (2), shuffle `groupBy` (3), обчислення агрегату і **заповнення кешу** (4), читання закешованих даних для `collect()` (5). Додатковий job — це матеріалізація кешу як окремої стадії AQE.
- **Job 6** — другий `collect()`: **лише 1 job**, дані беруться з кешу, застосовується `where("count>2")`. CSV не перечитується, shuffle не виконується (стадії позначені skipped).

## Висновок: що робить `cache()` і навіщо

`cache()` — лінива операція: вона позначає DataFrame для збереження в пам'яті, а саме збереження відбувається під час першої дії. Усі наступні дії над цим DataFrame читають готовий результат замість повторного читання файлу й повторних shuffle — у частині 3 другий `collect()` скоротився з 3 jobs до 1.

`cache()` варто використовувати, коли той самий DataFrame потрібен у кількох діях або в ітеративних обчисленнях. Ціна — зайнята пам'ять executor'ів, тому після використання кеш звільняють через `unpersist()`.
